**Recursive Gate-Execution Containment**

- `internal/gatecontext` is the single classifier for recursive pipeline control. It combines canonical registered gate common-directory identity with OS-authenticated IPC peer ancestry; `NO_MISTAKES_GATE` is diagnostic only. CLI preflight, daemon mutation ingress, gate init/eject, branch-sync mutation, and the managed pre-receive hook must all keep using that owner so marker removal, cwd changes, and direct pushes cannot bypass refusal. Read-only AXI status/logs, help, and doctor remain available. Regressions: `internal/gatecontext`, `TestGateStepCannotStartRecursivePipeline`.
- Every pipeline agent prompt receives the phase boundary from `internal/gateguidance`, and the generated user-level skill reuses the same owner. Step agents return only their assigned phase; the outer executor alone controls other validation, push, PR, and CI phases. Edit `internal/skill/skill.go`, then run `make skill`; never edit the generated skill directly.

**Filesystem and Paths**

- Use `filepath.Join`; respect `NM_HOME` for app state; directories are `0o755` and files `0o644` by convention.
- On macOS, path comparisons may need symlink resolution (`/var` vs `/private/var`); use `worktrees.Canonical`/`worktrees.Contains` wherever run worktree paths are compared, so one spelling matches everywhere.
- Run worktree placement (`worktree_roots`) is owned by `internal/worktrees`. Configuration decides it exactly once, at run creation (`Layout.Dir` in `RunManager.startRunWithIntentSource`), and the result is persisted in `runs.worktree_dir`; every later consumer - resume, step diff, startup cleanup, `procreap`, eject, gatecontext attribution - must read it back through `worktrees.RecordedDir` and never re-derive it from config, so a mid-flight edit can neither strand a parked run nor point a removal at a directory the run never used. An empty column means the default `<NM_HOME>/worktrees/<repoID>/<runID>`.
- `worktrees.CheckPlacement` is the single policy for an unusable root (inside `NM_HOME`, inside any registered checkout); `config.ValidateWorktreeRoots` owns what the config can judge alone. The daemon refuses to start on an unusable placement, so `init --worktree-root` must refuse exactly the same set or it prints a paste that takes the operator's CLI down, and EVERY `init` refuses to register a checkout that contains a configured root - the same state reached from the other direction. User-facing semantics live in `docs/src/content/docs/reference/global-config.md`. Regressions: `internal/worktrees`, `internal/config/config_worktree_roots_test.go`, `internal/daemon/worktree_roots_test.go`, `internal/gate/eject_sweep_test.go`, `internal/cli/init_test.go`.
- A run worktree is created only through `git.WorktreeAdd` (`internal/git/worktree_add.go`) and removed only through `git.WorktreeRemove` (`internal/git/worktree_remove.go`), never `git worktree add` or `git worktree remove` (startup cleanup alone falls back to `os.RemoveAll` of the working directory when that removal fails).
  Git builds and deletes a worktree's admin entry (`<common dir>/worktrees/<id>/`) in place, file by file, while other git processes walk the gate's worktrees.
  Every git command that enumerates them (the receive-pack of a push included) reads `worktrees/<id>/gitdir`, then checks that `worktrees/<id>/commondir` exists and reads it, and dies with `failed to read worktrees/<id>/commondir: <errno>` when the file is missing or still empty at the read; `<errno>` is whatever the reader had left (`Success`, `Numerical result out of range`, `No such file or directory`), so the text alone does not say which window it was.
  And the `git maintenance run --auto` git runs after every push prunes worktrees as soon as one entry is prunable (no `gitdir` and no `locked` file), and that prune deletes file by file again; git never prunes a locked entry.
  `git worktree remove` hit the first (a push right after a run ended failed), and `git worktree add` hit both: it writes the new entry's `gitdir` before its `commondir`, and it creates the entry's directory before its `locked` file, so a prune in between took the new entry and the add failed with `could not open` a file of its own entry for writing.
  The two functions share three rules, stated in `WorktreeAdd`'s doc comment, which a change to either must keep:
  an entry has a `gitdir` file (is listed) only while it is complete (removal unlists first, creation lists last);
  an entry without a `gitdir` file is locked for as long as it sits in `worktrees/` (removal writes the lock before it unlists, creation brings the lock in with the entry);
  an entry without a `gitdir` file enters and leaves `worktrees/` in one rename (creation renames a fully staged entry in; the sweep and a failed creation's undo rename an entry out into `no-mistakes-removed-worktrees/` and delete it there).
- The removal order is the fix for the first window and must stay: write the admin `locked` file and unlink the admin `gitdir` file first (git skips an entry without one), then the working directory with its `.git` file last (it names the admin directory, so a failed removal can be retried), then the admin directory except `commondir` (a reader that got past the unlink still reads it) and `locked`.
  The `locked` file is written before `gitdir` is unlinked and is load-bearing, since the unlisted leftover is otherwise prunable.
  That leftover is swept by a later removal on the same repository once its `locked` file is older than `removedWorktreeGrace` (a minute), and only when the file holds this package's own reason, so a worktree somebody else locked is left alone.
  The admin entry is found through the working directory's own `.git` file, which a process of the run can rewrite, so `adminEntryIsFor` uses it only when its `gitdir` file names that working directory back, or, with no `gitdir` file, when it holds the removal's lock reason (a removal that failed part way) or the creation's lock reason with a `gitdir.pending` that names that working directory back (a creation that died); anything else is refused with `ErrNotLinkedWorktree` before anything is written.
  A worktree whose working directory or `.git` file is already gone is therefore refused and stays registered.
- The creation order, on a gate whose `extensions.refstorage` is unset or `files`, closes both windows of `git worktree add` and must stay.
  Resolve the common directory, the commit (`<rev>^{commit}`) and the absolute path before anything is written, and refuse a path that exists and is not an empty directory, as git does.
  Stage the entry out of git's sight under `<common dir>/no-mistakes-new-worktrees/`: `locked` (`creatingWorktreeLockReason`), `commondir` (`../..`), `HEAD` (the commit, a detached HEAD as a files-format file), `gitdir.pending` (the future `gitdir`, a real path with forward slashes), and, when `extensions.worktreeConfig` is on, the gate's `config.worktree` without `core.bare` and `core.worktree`, which is what carries the pinned `core.hookspath` into the worktree and keeps the gate's `core.bare=true` out of it (`IsolateHooksPath` relies on that, as with git's own add).
  Rename it into `worktrees/<id>`, complete, locked and unlisted: `<id>` is git's naming (the base name with everything outside `[A-Za-z0-9._-]` made `-`, then `<id>1` to `<id>999` while taken, since a removed worktree's leftover holds its name for a minute), and every candidate is `Lstat`ed first because a rename replaces an empty directory.
  `worktrees/` is made again right before each rename, and again (a bounded number of times) when the rename failed because it is gone, since the same prune deletes `worktrees/` whenever it is empty, as on a gate's first run.
  Then make the working directory and its `.git` file, check out with `git --git-dir=<admin> --work-tree=<wt> reset --hard --no-recurse-submodules` (the repository named, never discovered), list by renaming `gitdir.pending` to `gitdir`, and unlock.
  No `post-checkout` hook runs, where git's add runs one; a gate's hooks directory holds only the managed `pre-receive` and `post-receive`.
  The paths written are always absolute, where git's add honours `worktree.useRelativePaths` (no gate sets it; the removal takes a relatively linked worktree either way).
  A creation that fails part way, a cancelled context included, undoes what this call did without using that context: the staging directory deleted, an entry already renamed in renamed into the trash and deleted, the working directory deleted or emptied, a listed one through `WorktreeRemove`.
- On a gate in another ref format (reftable) `WorktreeAdd` runs `git worktree add --detach` as before, because a `HEAD` written as a file is only correct for the files format, so both windows stay open there; a config read error fails the add closed.
  Hand-building a reftable entry, or creating every gate in the files format, would close that and are not verified.
- A creation that died (crash, kill) leaves a staging directory, an unlisted creation-locked entry, or a listed worktree still under the creation lock.
  `WorktreeRemove` of the working directory takes the unlisted entry (when its `.git` file was written) and the listed one, like any locked worktree.
  Otherwise the sweep, which runs only from `WorktreeRemove`, takes an unlisted creation-locked entry once its lock is older than `creatingWorktreeGrace` (a day) and a staging directory once its own mtime is; `sweepableAdminLock` picks the grace by the lock's reason (removal one minute, creation a day, any other lock never), because a creation in flight must never be swept.
- The reproduction loop is `TestWorktreeRemoveStressAgainstConcurrentPushes`: adds overlap pushes, removals and each other, and every failure fails it, counted by what the named worktree was doing at the time; it is skipped unless `NM_WORKTREE_REMOVE_STRESS` names a duration, `NM_WORKTREE_REMOVE_STRESS_GIT_ADD` and `NM_WORKTREE_REMOVE_STRESS_GIT_REMOVE` swap in git's own add and removal to see it fail, and its header owns the settings.
  The prune window lies between two system calls inside git's own add, so it has no deterministic test: `TestWorktreeAddListsTheWorktreeOnlyOnceItIsComplete` proves the property that closes it (the entry is locked and unlisted from its first appearance, and survives a prune mid-checkout), and the loop proves the failure.
  Regressions: `TestWorktreeAddListsTheWorktreeOnlyOnceItIsComplete`, `TestWorktreeAddChecksOutADetachedWorktree`, `TestWorktreeAddCopiesTheWorktreeConfigWithoutCoreBare`, `TestWorktreeAddRefusesAPathThatAlreadyHoldsFiles`, `TestWorktreeAddUndoesAFailedCreation`, `TestWorktreeAddUndoesACreationCancelledDuringItsCheckout`, `TestWorktreeAddSurvivesAPruneDeletingTheEmptyWorktreesDirectory`, `TestWorktreeAddTakesTheNextNameWhenItsEntryNameIsTaken`, `TestWorktreeAddSanitizesTheEntryName`, `TestWorktreeAddFallsBackToGitOnAnotherRefFormat`, `TestWorktreeRemoveKeepsWhatAReaderAlreadyListingTheWorktreeStillReads`, `TestWorktreeRemoveLeftoverSurvivesGitsOwnPruning`, `TestWorktreeRemoveUnlistsBeforeItDeletesAnything`, `TestWorktreeRemoveSweepsLeftoverAdminEntriesOnlyAfterTheGracePeriod`, `TestWorktreeRemoveRefusesADirectoryThatIsNotThisRepositorysWorktree`, `TestWorktreeRemoveRemovesALockedWorktree`, `TestWorktreeRemoveRefusesAnAdminEntryThatPointsAtAnotherWorktree`, `TestWorktreeRemoveRemovesAWorktreeLinkedWithRelativePaths`, `TestWorktreeRemoveRemovesAWorktreeWhoseCreationDied`, `TestWorktreeRemoveSweepsADeadCreationOnlyAfterItsGracePeriod`.

**Git on Bare Gate Repos (`safe.bareRepository`)**

- Agent harnesses and hardened CI inject `safe.bareRepository=explicit`, which forbids cwd-based discovery of bare repositories. Route every gate git call through `git.Run`, which detects a bare git dir and prepends `--git-dir=<dir>`; never shell out to git in a bare gate repo relying on `cmd.Dir` or `-C` discovery (issue #362).
- Startup gate migration is DB-authoritative with a strict validated `<id>.git` legacy fallback; it must reject non-gates before hook or Git mutation and use `git.RunBare` so a malformed directory cannot discover an ancestor worktree. Completed migrations carry the content-versioned gate-config stamp and normal restarts must stay filesystem-only for current gates. Regressions: `TestMigrateGateConfigsRejectsInvalidDirectoriesAndSkipsCurrentGates`, `TestColdDetachedStartupProductionGateCardinality`.
- Regressions: `TestRunOnBareRepoUnderSafeBareRepositoryExplicit`, `TestWorktreeAddRemoveOnBareRepoUnderSafeBareRepositoryExplicit`, `TestInitUnderSafeBareRepositoryExplicit`.

**`gh` PR-Targeting From the Bare Gate Repo (`internal/scm/github`)**

- The daemon runs `gh` from the detached bare gate repo whose HEAD is the default branch, so every PR-targeting command must name the exact PR explicitly: an empty positional makes `gh pr <verb>` infer the cwd branch (`main`) and return `no pull requests found for branch main` even when the feature PR's checks are green. `GetChecks`, `GetPRState`, `GetMergeableState`, and `UpdatePR` route through the shared `prSelector` (number, else URL, else fail closed) - never append a bare `pr.Number`/`pr.URL` that can be empty. This is the `gh` analogue of the git bare-gate-repo trap above.
- Regressions: `TestGetChecksTargetsKnownPRByURLWhenNumberMissing`, `TestPRTargetingReadsFailClosedWithoutIdentity`, `TestPRStateAndMergeableTargetKnownPRByURL`, `TestUpdatePRTargetsKnownPRByURLWhenNumberMissing`, `TestUpdatePRFailsClosedWithoutIdentity`.

**Post-Receive Hook Gate Path Resolution (`internal/git/hook.go`)**

- The hook's `--gate` value must never come from a bare `$(pwd)`: Git can invoke `post-receive` from a cwd that collapses to `.` (issue #269), which the daemon rejects and the pipeline silently never starts. The hook script resolves an absolute gate dir (git first, hook location fallback), and `normalizeNotifyGatePath` in `internal/cli/daemon_cmd.go` is an independent second layer that absolutizes whatever an already-installed older hook sends.
- Regressions: `TestPostReceiveHook_ResolvesAbsoluteGateDir`, `TestPostReceiveHook_FallsBackToHookLocationForGateDir`, `TestNormalizeNotifyGatePathResolvesLegacyDotGate`.
